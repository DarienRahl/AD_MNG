# Test lab (Samba AD DC)

A disposable domain controller for development and integration tests – **never** run these scripts on a computer that
belongs to a real domain (they overwrite `/etc/samba/smb.conf` and `/etc/krb5.conf`).

```bash
sudo LAB_USERS=400 LAB_COMPUTERS=250 LAB_BULK_USERS=0 tools/testlab/setup-samba-dc.sh
```

The script installs Samba (Ubuntu 24.04), creates the `CONTOSO.TEST` domain and loads data generated by
`generate_ldif.py` (deterministic, seed 2026):

```
DC=contoso,DC=test
└── OU=Firma
    ├── OU=Pracownicy        OU=IT, Księgowość, Sprzedaż, Kadry, Marketing, Logistyka, Zarząd
    ├── OU=Komputery         OU=Warszawa, Kraków, Gdańsk, Wrocław, Poznań  (each: Laptopy, Stacjonarne)
    ├── OU=Serwery
    ├── OU=Grupy             OU=Bezpieczeństwa, OU=Dystrybucyjne (global/domain local/universal groups, nesting)
    ├── OU=Konta serwisowe   test and service accounts
    ├── OU=Wyłączone
    ├── OU=Kontakty
    └── OU=Masowe            only when LAB_BULK_USERS > 0 (performance tests, group with > 1500 members)
```

| Account | Password | Permissions |
|---|---|---|
| `Administrator@contoso.test` | `P@ssw0rd!2026` | Domain Admin |
| `helpdesk.test@contoso.test` | `Passw0rd!Lab2026` | delegation on `OU=Pracownicy`: password reset, unlock, `pwdLastSet`, phone numbers |
| `odczyt.test@contoso.test` | `Passw0rd!Lab2026` | regular user – read only |

A few accounts in `OU=Sprzedaż` are locked out on purpose (lockout threshold = 5).

Integration tests:

```bash
export ADMNG_TEST_LDAP_SERVER=127.0.0.1
export ADMNG_TEST_LDAP_USER='Administrator@contoso.test'
export ADMNG_TEST_LDAP_PASSWORD='P@ssw0rd!2026'
dotnet test tests/AdMng.Directory.IntegrationTests
```

The lab allows simple bind without TLS solely so that `ldapsearch -x` and the tests on Linux work. In production the
application uses Negotiate (Kerberos) with signing and encryption, or LDAPS.

If the lab does not respond on port 389 (e.g. after a container restart), start it again with the command
`samba -D` and wait until port 389 accepts connections.

### Kerberos (SASL GSSAPI) over LDAP

AdMng Watchdog on Linux connects to the DC over LDAP 389 with Kerberos and SASL encryption (GSSAPI, SSF ≥ 56). For that,
the DC account must have the SPNs `ldap/<DC name>` (e.g. `ldap/vm.contoso.test`), and the full DC name must resolve.
Earlier the lab had only `HOST/…` SPNs and GSSAPI failed with `Server not found in Kerberos
database`. The cause: Samba adds the `ldap/` SPNs with the `dnsupdate` task, which runs `samba_spnupdate` through
`#!/usr/bin/python3`; when `/usr/bin/python3` is a different version than the one the Samba modules were built for (here
3.13 instead of 3.12), the script silently fails with `No module named 'ldb'`. In addition, `--dns-backend=NONE` produces
no record for the DC name.

`setup-samba-dc.sh` now performs both steps itself (without changing `smb.conf`). In an older, running lab it is enough
to do this once (as root):

```bash
dc=$(ldapsearch -x -LLL -H ldap://127.0.0.1 -b '' -s base dnsHostName | sed -n 's/^dnsHostName: //p')
getent hosts "$dc" || echo "127.0.0.1 $dc" >> /etc/hosts
/usr/bin/python3.12 /usr/sbin/samba_spnupdate --verbose      # the interpreter with the Samba modules
```

Verification (a private `krb5.conf` with `kdc = <DC name>`, the ticket in a private cache):

```bash
KRB5_CONFIG=… KRB5CCNAME=FILE:… kinit Administrator@CONTOSO.TEST
LDAPCONF=… ldapsearch -Y GSSAPI -H "ldap://$dc" -b 'DC=contoso,DC=test' -s base dn   # SASL SSF: 256
```

`LDAPCONF` points to a file with `SASL_NOCANON on` and `SASL_SECPROPS minssf=56,noanonymous,noplain` (like
`packaging/admng-watchdog/etc/ldap.conf`, in the package `/etc/admng-watchdog/ldap.conf`). The tests of the keytab tool
and GSSAPI are described in [`watchdog/README.md`](watchdog/README.md) ("Service account and keytab").

### Cleaning up after tests

Every test run works in its own OU directly under the domain: `OU=AdMngIntegration-<UTC time>-<random>`
(`tests/AdMng.Directory.IntegrationTests`) or `OU=WatchdogIT-<UTC time>-<random>`
(`tests/AdMng.Watchdog.IntegrationTests`), so parallel runs (several working copies, CI jobs) do not
interfere with each other. The OU description identifies the test process (`[run <host> pid <id> started <time>]`). At
start, a run deletes the OUs of runs that have finished – the process on the same host is no longer running (an
aborted run) or the OU is older than 2 hours (the owner is on another host, old `OU=AdMngIntegration` from earlier
versions) – and leaves the OUs of runs in progress alone. At the end it deletes its own OU.

Samba executes only one write transaction at a time (in the lab about 0.1 s per deleted object) and aborts every
LDAP request after 300 s. Deleting a tree on the server side (the tree delete control) for an OU with thousands of
objects – the directory test run creates two groups of 1600 members and 3200 contacts, which is about 5 minutes of
work – therefore ended with a `timeLimitExceeded` error, left objects behind and, for that whole time, blocked the writes
of other runs. For that reason the tests delete trees on the client side (`tests/AdMng.Directory.IntegrationTests/Infrastructure/LabCleanup.cs`): groups
lose their members in a single modification, then every object is deleted separately, deepest first, with a 10-minute limit
per request. Each request takes a fraction of a second, so the writes of other runs interleave with them. If the lab
is busy (timeout, LDAP busy) or not running, the run ends with a message saying what to do; leftovers
that could not be deleted are only reported (diagnostic messages:
`dotnet test ... -- xUnit.DiagnosticMessages=true`) and the next run will delete them.

Manually (only the tests' own OUs, never `OU=Firma`):

```bash
ldapsearch -x -H ldap://127.0.0.1 -D 'Administrator@contoso.test' -w 'P@ssw0rd!2026' \
  -b 'DC=contoso,DC=test' -s one '(|(ou=AdMngIntegration*)(ou=WatchdogIT-*))' dn description whenCreated
ldapdelete -x -H ldap://127.0.0.1 -D 'Administrator@contoso.test' -w 'P@ssw0rd!2026' -r 'OU=WatchdogIT-…,DC=contoso,DC=test'
```

## AdMng Watchdog

The **AdMng Watchdog** monitoring service is run against this lab with the scripts from
[`watchdog/`](watchdog/README.md): Mailpit as an SMTP server with a message preview, a receiver of webhooks and Teams cards,
a change scenario in the disposable `OU=WatchdogDemo` and optional real Kerberos.

```bash
tools/testlab/watchdog/run-watchdog-lab.sh --reset --background   # service + Mailpit + receiver
tools/testlab/watchdog/configure-lab.sh --test                    # SMTP, channels, recipients (through the API)
tools/testlab/watchdog/lab-scenario.sh --verify                   # directory changes and verification of notifications
tools/testlab/watchdog/run-watchdog-lab.sh --stop
```

The service's integration tests (`tests/AdMng.Watchdog.IntegrationTests`) additionally need a read-only account and
Mailpit:

```bash
tools/testlab/watchdog/start-mailpit.sh
export ADMNG_TEST_LDAP_READONLY_USER='odczyt.test@contoso.test' ADMNG_TEST_LDAP_READONLY_PASSWORD='Passw0rd!Lab2026'
export ADMNG_TEST_SMTP_HOST=127.0.0.1 ADMNG_TEST_SMTP_PORT=1025 ADMNG_TEST_MAILPIT_API=http://127.0.0.1:8025
dotnet test tests/AdMng.Watchdog.IntegrationTests
```
